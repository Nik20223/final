# Restful Booker Platform: автоматизация тестирования и непрерывная интеграция

Документ описывает, что представляет собой проект целиком: из каких слоёв
состоит тестовый фреймворк, сколько в нём тестов и откуда берутся эти цифры, как
устроена генерация данных, как проходит сборка в Jenkins и что развёрнуто на
сервере. Структура каталогов вынесена в отдельный файл `PROJECT_STRUCTURE.md`,
развёртывание — в `deploy/README.md`.

## 1. Что тестируется

Тестируется учебная платформа **Restful Booker Platform** — веб-приложение для
бронирования номеров. Она состоит из фронтенда и нескольких независимых
Java-сервисов, каждый со своим HTTP API:

| Сервис | Порт | Назначение |
|---|---|---|
| UI | 80 | Публичная часть и админ-панель |
| booking | 3000 | Брони |
| room | 3001 | Номера |
| branding | 3002 | Оформление |
| auth | 3004 | Авторизация и токены |
| report | 3005 | Отчёты по занятости |
| message | 3006 | Сообщения |

Такое деление — главная особенность задачи. Сервисы общаются по сети, у каждого
свой жизненный цикл, и это даёт три разных уровня проверок: доступность сервисов
(health), контракты их API и сквозные пользовательские сценарии через браузер.

## 2. Стек

- **pytest** — движок тестов, маркировка, параметризация, фикстуры.
- **Selenium WebDriver** — UI-тесты, паттерн Page Object Model.
- **requests** — API-тесты.
- **Faker** — генерация тестовых данных.
- **Allure** — отчётность.
- **Docker** — стенд и агент CI.
- **Jenkins** — непрерывная интеграция.

## 3. Архитектура тестового фреймворка

Фреймворк разделён на слои, каждый со своей ответственностью. Тесты ничего не
знают про HTTP и локаторы — они говорят на языке предметной области.

```
config/    адреса, таймауты, учётные данные   ← читается всеми слоями
utils/     генерация данных, фабрика браузера
api/       клиенты HTTP-сервисов              ┐
pages/     объекты страниц                     ├ инструменты
conftest.py фикстуры, жизненный цикл          ┘
tests/     сами тесты                         ← только сценарии и проверки
```

Ключевое решение — **тонкие тесты**. В тестовом файле нет ни URL, ни CSS-селекторов,
ни склейки запросов. Тест выглядит так:

```python
def test_update_room_price_from_admin(self, admin, room):
    page = RoomDetailsPage(admin).open(room["roomid"])
    page.start_edit().set_price(777).save()

    updated = RoomDetailsPage(admin).open(room["roomid"])
    assert updated.room_price() == "777"
```

Всё, что относится к устройству страницы, спрятано в `RoomDetailsPage`, всё, что
относится к данным, — в фикстуре `room`. Благодаря этому изменение вёрстки или
адреса сервиса правится в одном месте, а не в тридцати тестах.

## 4. Тестовые наборы: сколько тестов и откуда берутся цифры

Всего в проекте **39 тестов**. Раскладка по файлам:

| Файл | Тестов | Откуда столько |
|---|---|---|
| `tests/api/test_health_api.py` | 6 | 1 функция × 6 сервисов через `parametrize` |
| `tests/api/test_auth_api.py` | 5 | 5 методов |
| `tests/api/test_booking_api.py` | 8 | 8 методов |
| `tests/api/test_room_api.py` | 7 | 7 методов |
| `tests/api/test_report_api.py` | 3 | 3 метода |
| `tests/ui/test_login_ui.py` | 3 | 3 метода |
| `tests/ui/test_booking_ui.py` | 2 | 2 метода |
| `tests/ui/test_rooms_ui.py` | 3 | 3 метода |
| `tests/ui/test_room_details_ui.py` | 2 | 2 метода |
| **Итого** | **39** | |

Обратите внимание: файлов девять, а тестов тридцать девять. Это не
несоответствие, а два разных механизма pytest.

**Файл — это набор, а не тест.** Каждый метод с префиксом `test_` pytest считает
отдельным тестом. В `test_booking_api.py` восемь таких методов, и в отчёте это
восемь независимых строк.

**Один метод может развернуться в несколько тестов.** Это делает
`@pytest.mark.parametrize`. Самый наглядный пример — проверка доступности
сервисов:

```python
SERVICES = [config.BOOKING_API_URL, config.ROOM_API_URL, config.AUTH_API_URL,
            config.BRANDING_API_URL, config.REPORT_API_URL, config.MESSAGE_API_URL]

@pytest.mark.parametrize("base_url", SERVICES)
def test_service_is_up(self, base_url):
    client = ApiClient(base_url)
    ...
```

В файле одна функция, но `parametrize` запускает её шесть раз — по разу на каждый
сервис, с отдельным именем и отдельным результатом в отчёте. Отсюда 1 функция = 6
тестов.

### Маркеры и отбор наборов

Наборы отбираются маркерами. Они объявлены в `pytest.ini`:

```ini
markers =
    ui: UI-тесты на Selenium
    api: API-тесты
    smoke: дымовые тесты
    regression: регрессионные тесты
```

В каждом файле стоит `pytestmark`, а в Jenkinsfile стадии запускают pytest с
ключом `-m`. Например, `pytest -m ui` выполнит только UI-набор.

Маркеры можно ставить и по нескольку сразу. В `test_health_api.py` их два:

```python
pytestmark = [pytest.mark.api, pytest.mark.smoke]
```

Отсюда важное следствие. Health-тесты попадают и в дымовой набор, и в API-набор,
поэтому за одну сборку они выполняются дважды: сначала как быстрый гейт на
стадии `Health check`, потом ещё раз в составе `API tests`. Если сложить цифры из
лога сборки, получится 6 + 29 + 10 = 45 выполнений при 39 уникальных тестах. Это
осознанный компромисс: дымовой прогон за четверть секунды отсекает лежащий стенд
раньше, чем запустится Selenium.

Маркер `regression` объявлен, но пока не используется ни в одном тесте — задел на
будущее.

## 5. Параметризация: два разных уровня

Слово «параметризация» здесь означает две независимые вещи.

**Параметризация данных** — `@pytest.mark.parametrize`. Набор значений передаётся
в аргумент, pytest размножает тест. Сейчас применена в health-проверках (шесть
сервисов), но механизм общий и распространяется на любой набор входных данных.

**Параметризация прогона** — параметры сборки Jenkins. Они едут по цепочке:

```
Jenkinsfile (params: BASE_URL, HEADLESS)
        ↓ environment
RBP_UI_URL, RBP_API_HOST, RBP_HEADLESS
        ↓ os.getenv
config/config.py
        ↓
фикстуры и клиенты
```

Благодаря этому один и тот же код гоняется и против локального стенда на
`docker compose`, и против публичного сервера, и с окном браузера, и без него. По
умолчанию `BASE_URL = http://localhost` — это работает потому, что контейнер
Jenkins запущен с `--network host` и `localhost` для него означает сам сервер.

## 6. Генерация тестовых данных

Тесты работают против живого стенда с настоящей базой, поэтому данные обязаны
быть уникальными. Иначе тесты начнут мешать друг другу: конфликты броней по
датам, «мигающие» проверки, зависимость от порядка запуска.

За это отвечает `utils/data_generator.py`. Ядро — уникальный суффикс:

```python
def unique_token():
    """Короткий уникальный суффикс, чтобы данные не пересекались."""
    return uuid4().hex[:8]
```

На его основе строятся остальные генераторы:

```python
def room_name():
    return f"QA-Room-{unique_token()}"

def contact():
    token = unique_token()
    return {"firstname": f"Qa{token[:6]}", "lastname": f"Test{token[:6]}",
            "email": f"qa.{token}@example.com",
            "phone": fake.numerify("#" * PHONE_LENGTH)}
```

Константы `FIRSTNAME_MAX = 18`, `LASTNAME_MAX = 30`, `PHONE_LENGTH = 11` — не
украшение, а подгонка под валидацию сервиса: слишком длинное имя он отклонит, и
тест упадёт по чужой причине. Описание комнаты и телефон генерирует Faker.

Даты вынесены в отдельную функцию, и смещение каждый раз разное:

```python
# tests/ui/test_booking_ui.py
checkin, checkout = future_dates(start_in_days=60, nights=2)

# tests/api/test_report_api.py
checkin, checkout = future_dates(start_in_days=90, nights=2)
```

Плюс шестьдесят и плюс девяносто дней выбраны специально: периоды броней разных
тестов не пересекаются, поэтому отчёты по занятости не зависят от порядка
выполнения.

Отдельно стоит подчеркнуть **обратный случай**. В `tests/api/test_booking_api.py`
данные наоборот фиксированные — `Ivan`, `Petrov`, даты `2030-01-10`:

```python
def test_conflicting_dates_are_rejected(self, booking_api, login, created_booking):
    response = booking_api.create(booking_payload())
    assert response.status_code == 409
```

Тесту на конфликт дат нужно дважды отправить одну и ту же бронь. Здесь
фиксированные данные — не небрежность, а условие работы проверки. Это хорошая
иллюстрация того, что выбор между генерацией и константой диктуется смыслом теста.

## 7. Инфраструктура тестов

### `conftest.py` — жизненный цикл

Семь фикстур и один хук:

- `driver` — поднимает WebDriver, отдаёт тесту, после теста сохраняет скриншот при
  падении и закрывает браузер;
- `admin` — логинит администратора и ждёт перехода в панель;
- `api_session` — общая `requests.Session` для всех API-клиентов;
- `api_client`, `auth_api`, `booking_api`, `room_api`, `report_api` — клиенты
  поверх этой сессии.

Сессия сделана общей не для экономии. Сервис авторизации выдаёт токен в cookie, и
именно на общей сессии он становится доступен остальным клиентам — повторить
логин не требуется.

Скриншоты устроены через хук:

```python
@pytest.hookimpl(wrapper=True)
def pytest_runtest_makereport(item, call):
    report = yield
    setattr(item, f"rep_{report.when}", report)
    return report
```

Результат каждой фазы теста сохраняется рядом с ним, а затем `_take_screenshot`
проверяет, упал ли тест, и только тогда пишет PNG в `screenshots/` и прикладывает
его к Allure. Поэтому в артефактах сборки нет скриншотов успешных тестов.

### `utils/`

- `driver_factory.py` — собирает WebDriver. Поддержаны Chrome и Firefox, режим
  берётся из конфига. Для Chrome выставляются размер окна 1920×1080 и флаг
  `--no-sandbox` — последний обязателен в контейнере, где браузер стартует под
  root, иначе Chrome не запускается.
- `data_generator.py` — генерация данных, разобрана выше.

### `api/` — клиенты сервисов

- `api_client.py` — обёртка над `requests.Session`: базовый URL, таймаут по
  умолчанию, заголовок `Accept: application/json`, методы `get/post/put/patch/delete`.
- `auth_api.py` — `login()`, `validate()`, `logout()`. При неверном пароле бросает
  `AuthError` с сохранённым HTTP-статусом, чтобы тест мог проверить код ответа.
- `booking_api.py` — CRUD броней плюс `get_all(room_id)`,
  `unavailable(checkin, checkout)` и `summary()`.
- `room_api.py` — CRUD номеров.
- `report_api.py` — отчёты по одной комнате и по всем.

### `pages/` — Page Object Model

- `base_page.py` — базовые операции: `open`, `find_element`, `wait_for_element`,
  `click`, `type_text`, `get_text`, `is_element_visible`. Все ожидания идут через
  `WebDriverWait`, ни одного `sleep` — это принципиально, иначе тесты становятся
  медленными и нестабильными. Клик сделан с двумя предосторожностями: элемент
  прокручивается в центр экрана, а если по нему всё равно не попасть
  (`ElementClickInterceptedException`), клик выполняется через JavaScript.
- `login_page.py`, `room_page.py`, `booking_page.py`, `room_details_page.py` — по
  классу на страницу; локаторы и действия живут внутри класса, тесты оперируют
  смысловыми методами вроде `create_room()` и `wait_for_room_removed()`.

## 8. Непрерывная интеграция

### Стадии

Джоба `rbp-tests` — Pipeline from SCM, скрипт берётся из `Jenkinsfile` в корне
репозитория. Стадии идут строго последовательно:

```
1. Checkout      checkout scm
2. Install       python3 -m venv .venv && pip install -r requirements.txt
3. Health check  pytest -m smoke --alluredir=allure-results --clean-alluredir
4. API tests     pytest -m api   --alluredir=allure-results
5. UI tests      pytest -m ui    --alluredir=allure-results
post always      archiveArtifacts screenshots/**  +  allure
```

Порядок подчинён принципу «сначала дешёвое». Зависимости ставятся один раз. Затем
дымовая проверка за четверть секунды убеждается, что все шесть сервисов живы, — и
если стенд лежит, сборка падает, не тратя минуту на запуск браузера. Дальше идут
API-тесты (около полутора секунд) и только потом UI-тесты (около сорока секунд).

Ключ `--clean-alluredir` стоит только на первой стадии: он очищает каталог
результатов, а последующие стадии в него дописывают. Так в один отчёт Allure
попадают все три набора.

Фактические длительности из зелёной сборки: health — 0.24 с, API — 1.4 с,
UI — 41 с. Сборка целиком занимает около 65 секунд.

### Параметры и запуск

Параметры сборки: `BASE_URL` (по умолчанию `http://localhost`) и `HEADLESS`
(по умолчанию `true`). Ограничения конвейера — таймаут 45 минут,
`disableConcurrentBuilds()` (два прогона не должны драться за один стенд) и
хранение последних 20 сборок.

Запуск автоматический: `pollSCM('H/15 * * * *')` опрашивает ветку `main` в GitHub
и ставит сборку в очередь, когда появляется новый коммит. Задержка до 15 минут —
плата за простоту: не требуется, чтобы GitHub мог достучаться до Jenkins. При
необходимости мгновенного старта вместо опроса настраивается вебхук.

### Артефакты

- **Allure-отчёт** — пошаговый отчёт по каждому тесту с вложениями.
- **`screenshots/**`** — снимки упавших UI-тестов, архивируются как артефакты и
  прикладываются к отчёту.

## 9. Развёртывание

На сервере работают два независимых контура, и их важно не путать.

**Стенд платформы** — сам Restful Booker Platform. Поднимается скриптом
`deploy/deploy.sh` на чистой Ubuntu: установка Docker, добавление swap, получение
исходников, сборка jar-ников и запуск через `docker compose`. Скрипт
идемпотентен: повторный запуск обновляет исходники и пересобирает стенд.

**Jenkins** — отдельный контейнер, собранный из `deploy/jenkins.Dockerfile`.
Внутри официальный LTS с JDK 21, Python с `venv` (конвейер создаёт виртуальное
окружение), Chrome для UI-тестов и нужные плагины.

Связывает контуры флаг `--network host`: для контейнера Jenkins `localhost` — это
сам сервер, поэтому он видит стенд на 80-м порту и на портах 3000–3006 без
каких-либо настроек сети.

Состав `deploy/`:

| Файл | Назначение |
|---|---|
| `deploy.sh` | Идемпотентное развёртывание стенда с нуля |
| `assets.Dockerfile` | Свой Dockerfile фронтенда (см. раздел 10) |
| `jenkins.Dockerfile` | Образ Jenkins с Python, Chrome и плагинами |
| `jenkins-casc.yaml` | Настройки Jenkins как код: админ, права, адрес, установка Allure |
| `jenkins-job.xml` | Описание джобы: SCM, ветка, путь к Jenkinsfile |
| `jenkins-create-job.sh` | Создание джобы через REST (упирается в crumb, см. раздел 10) |
| `.env.example` | Шаблон локальных секретов |
| `README.md` | Документация развёртывания |

### Секреты

Пароль администратора Jenkins в репозитории не хранится. Он подставляется в
`jenkins-casc.yaml` из переменной окружения:

```yaml
      users:
        - id: "admin"
          password: "${JENKINS_ADMIN_PASSWORD}"
```

Значение задаётся в двух местах: локально в `deploy/.env` (файл в `.gitignore`,
используется скриптами) и на сервере в `/root/jenkins.env`, откуда его читает
контейнер. Шаблон — `deploy/.env.example`.

## 10. Трудности и решения

Этот раздел — про проблемы, которые не видны в коде, но определяют, работает
система или нет.

**Фронтенд обращался к `localhost` вместо сервисов.** `next.config.js` запекает
адреса сервисов в `rewrites` на этапе сборки, а в апстримном `assets/Dockerfile`
переменные `BOOKING_API`…`REPORT_API` объявлены только в финальном слое `runner`.
Из-за этого в образ попадали адреса `http://localhost:300X`, и почти все прокси
отдавали 500 — страница бронирования бесконечно крутила спиннер. Решение — свой
`assets.Dockerfile`, где `ENV` объявлены уже в базовом слое `base`.

**Java 26 и сборка jar.** Dockerfile'ы сервисов делают `COPY target/*-exec.jar`,
то есть jar обязаны существовать до `docker build`. Проект требует Java 26,
которой нет в репозиториях Ubuntu, поэтому Maven собирает в образе
`maven:3-eclipse-temurin-26`, а зависимости кэшируются в томе `rbp-m2`. Стенд
перед сборкой останавливается, чтобы шесть JVM не конкурировали за память.

**Chrome не запускался под root.** Решение — флаг `--no-sandbox` в фабрике
драйвера.

**pytest ломал stdin дочернего процесса.** При захвате вывода на уровне файловых
дескрипторов `selenium-manager` не мог запустить Chrome. В `pytest.ini` добавлен
`--capture=sys`, и рядом оставлен комментарий с объяснением — иначе эту строку
легко удалить как «лишнюю».

**Jenkins поднимался полностью открытым.** Флаг
`-Djenkins.install.runSetupWizard=false` отключает мастер настройки, а мастер —
единственное, что создаёт администратора. В результате инстанс на публичном адресе
стартовал с `SecurityRealm=None` и `AuthorizationStrategy=Unsecured`. Решение —
описать доступ в `jenkins-casc.yaml` и передать путь переменной
`CASC_JENKINS_CONFIG`: без неё плагин configuration-as-code конфиг не читает.

**Неверный ключ в конфиге останавливал Jenkins.** Атрибут установщика Allure
называется `version`, а не `allureVersion`. Ошибка в одном ключе приводила к
`Failed ConfigurationAsCode.init` и `Failed to initialize Jenkins` — контейнер
уходил в цикл перезапусков. Проверять правки конфигурации нужно на живом стенде.

**git отказывался работать с репозиторием.** Сначала «dubious ownership» (каталог
принадлежал root, а Jenkins работает под другим пользователем), затем явный запрет
checkout из локального каталога. Первое решилось сменой владельца, второе — только
переходом на репозиторий GitHub: разрешать локальные checkout'ы пришлось бы
отдельным флагом, ослабляющим проверку безопасности.

**REST API не принимает POST с Basic-аутентификацией.** Получить crumb удаётся, но
запрос всё равно отклоняется с 403 — Jenkins защищается от фиксации сессии.
Поэтому джоба создаётся копированием `config.xml` в `JENKINS_HOME`, а сборка
запускается через CLI. Обе дороги описаны в `deploy/README.md`.

**Bind-mount рвётся при пересоздании каталога.** Если удалить и заново создать
каталог, смонтированный в контейнер, монтирование остаётся привязано к старому
inode, и внутри контейнера путь становится нечитаемым. Лечится перезапуском
контейнера.

**Пароль утёк в публичный репозиторий.** Пароль администратора Jenkins был записан
литералом сразу в три файла. Пока репозиторий был приватным, это терпелось; после
перехода на публичный репозиторий доступ к CI получил бы любой. Решение — вынести
значение в переменные окружения (см. раздел 9). Следует учитывать, что значение
осталось в истории коммитов, поэтому пароль имеет смысл сменить.

## 11. Карта конфигурации

| Файл | Что настраивает |
|---|---|
| `config/config.py` | Все адреса, учётные данные, таймауты, браузер, headless |
| `pytest.ini` | `testpaths`, маркеры, режим захвата вывода |
| `requirements.txt` | Зависимости Python |
| `Jenkinsfile` | Стадии, параметры, триггер, публикация отчётов |
| `deploy/jenkins-casc.yaml` | Аккаунт администратора, права, адрес инстанса, Allure |
| `deploy/jenkins-job.xml` | Описание джобы |
| `deploy/.env` | Локальные секреты (в `.gitignore`) |
| `/root/jenkins.env` | Переменные окружения контейнера Jenkins |

Практически каждое значение в `config/config.py` переопределяется переменной
окружения с префиксом `RBP_`: `RBP_API_HOST`, `RBP_UI_URL`, `RBP_BOOKING_URL`,
`RBP_ROOM_URL`, `RBP_AUTH_URL`, `RBP_REPORT_URL`, `RBP_BRANDING_URL`,
`RBP_MESSAGE_URL`, `RBP_ADMIN_URL`, `RBP_ADMIN_USERNAME`, `RBP_ADMIN_PASSWORD`,
`RBP_DEFAULT_TIMEOUT`, `RBP_PAGE_LOAD_TIMEOUT`, `RBP_BROWSER`, `RBP_HEADLESS`.
Это и есть точка подключения любого нового стенда.

## 12. Как запустить

Локально, против стенда из `deploy.sh`:

```bash
python -m pip install -r requirements.txt

python -m pytest                          # все 39 тестов
python -m pytest -m smoke                 # только дымовые (6)
python -m pytest -m api                   # только API (29)
python -m pytest -m ui                    # только UI (10)
python -m pytest --alluredir=allure-results
```

Против другого стенда — переменными окружения:

```bash
RBP_API_HOST=http://localhost RBP_UI_URL=http://localhost python -m pytest
```

В Jenkins — джоба `rbp-tests`; сборка стартует сама при коммите в `main` либо
вручную из интерфейса.

## 14. Что можно развивать дальше

- **Наглядность интерфейса.** Плагин Pipeline Graph View даёт интерактивный граф
  стадий; публикация JUnit XML добавит график Test Result Trend и счётчики
  прошедших и упавших тестов.
- **Мгновенный запуск.** Вебхук GitHub вместо опроса по расписанию.
- **Безопасность.** Смена пароля администратора и ограничение доступа к порту
  8080; в перспективе — TLS через обратный прокси.
- **Полнота наборов.** Задействовать маркер `regression`, развести дымовой и
  API-наборы так, чтобы health-тесты не выполнялись дважды.
